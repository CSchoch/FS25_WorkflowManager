## Key Learnings

- **Vehicle sleep handling:** `raiseActive()` called every 500ms in `WMExecutor:update()` for all `activeVehicles` is sufficient to keep waiting vehicles awake. A separate global wait poller (`g_currentMission:addUpdateable`) is NOT needed and NOT implemented. Do not introduce `ensureWaitPollerActive` / `globalWaitPoller` — they were planned but abandoned; raiseActive() in the update loop handles all WAITING states.
- **Leader vehicle save/restore identity (SUPERSEDED 2026-07-13):** The XML index parsed from `savegame.key` (`wmXmlIndex`, stored as `#leaderVehicleXmlIndex`) is only stable *within one load* — it is NOT stable across separate save sessions. If the composition/order of `vehicles.xml` changes between saves (vehicle bought/sold, implement added elsewhere in the list, etc.), the same numeric index can point to a completely different vehicle on the next load. This caused bug-119 ("Steyer tractor lost its leader"): a stale index resolved to an unrelated vehicle with no workflow, so the pending-leader poller could never match it and the follower was stuck in `waiting_for_leader` forever. **Fix:** use the vehicle's own engine-assigned `vehicle.uniqueId` (same value as the `uniqueId="..."` attribute FS25 already writes on every `<vehicle>` element) as the primary leader identity — read/compare it directly off the live vehicle object, do NOT mirror/cache it under a new field name. Saved as `#leaderVehicleUniqueId`, with `pendingLeaderUniqueId` mirroring the existing `pendingLeaderXmlIndex`/`pendingLeaderWorkflowId` deferred-resolution fields. The old `#leaderVehicleXmlIndex` → legacy `#leaderVehicleIndex` → legacy `#leaderWorkflowId` chain is kept as a read-only fallback for saves written before this fix, unchanged. Do NOT use `g_currentMission.vehicles` array position either (unstable — map scripts can prepend vehicles, shifting indices). Do NOT use workflow ID alone (ambiguous — multiple vehicles can run the same workflow).
- **`onPostLoad` ordering:** FS25 calls `onPostLoad` for each vehicle as it loads — order is not guaranteed. A vehicle that has a leader may load BEFORE the leader, so leader resolution must be deferred. `tryResolvePendingLeader` runs every 500ms in the WMExecutor update loop; the standard update tick handles all pending resolution without a separate poller.
- **STATUS_WAITING_FOR_MAIN:** Added 2026-06-17. Support vehicle enters this status when main is on a step with no support sub-steps OR when all sub-steps for the current step are done. Pauseable. Saved to XML as `#status`. Poller detects `waitingForMainStepIndex != main.currentStep` AND `#supportSteps > 0` to trigger resume via `onMainStepChanged`. When support starts a sub-step, `executeCurrentStep` sets `status = RUNNING` explicitly before dispatching to `startAutoDriveStep` / `startCourseplayStep`.
- **Test poll triggering:** In executor tests, replace `WMExecutor.updateTimer=0; WMExecutor:update(500)` poll patterns with `triggerPoll()` (defined in the spec as a local helper). The `WorkflowManagerSpec_spec.lua` WMExecutor stub does NOT need `ensureWaitPollerActive` — that method does not exist in production.
- **HUD design intent (2026-07-13):** User wants the HUD header to show only the WorkflowManager title, not the controlled vehicle's name (vehicle context is already obvious from being in the seat). Step info line shows a compact `[AD]`/`[CP]`/`[WM]` type tag (via `WorkflowManager:getStepTypeShortcut(stepType)`) ahead of the step description — `WM` covers internal marker steps (wait_for_leader, unlock_follower), not just literal "WM" steps. When `STATUS_WAITING_FOR_LEADER`, the status line appends the leader vehicle's name (`activeData.leaderVehicle:getName()`) so the player knows who they're waiting on. Same treatment added for `STATUS_WAITING_FOR_MAIN` (support vehicle waiting on main), via `WMExecutor:getMainActiveDataForWorkflow(workflow.id).vehicle`.
- **Switching player-controlled vehicle:** base-game `Player` class exposes `player:requestToEnterVehicle(vehicle)` — confirmed used by both AutoDrive (`AutoDrive.requestToEnterVehicle` in `AutoDriveUtilFuncs.lua`, via `AutoDrive.getPlayer()`) and Courseplay (`CpHudInfoTexts:enterVehicle` in `CpHudInfoTexts.lua`, calls `g_localPlayer:requestToEnterVehicle(vehicle)` directly). WM HUD uses the same `g_localPlayer:requestToEnterVehicle(vehicle)` call (no AD/CP dependency needed) to let players click a leader/main vehicle name in the HUD and jump into it.
- **`webeditor/` is a separate, hand-maintained JS mirror of the Lua step-type system — new step types don't propagate automatically.** `webeditor/app.js` has its own `STEP_TYPES` array and its own `isMarkerType()` predicate (semantically identical to Lua's `WorkflowManager:isTargetlessStepType`, but a completely separate implementation with no shared code). Whenever a new step type is added in-game, it must be added here too: `STEP_TYPES` array, `isMarkerType()` widened if targetless, `stepTypeLabel()` switch, i18n `typeX`/`xInfo` keys (en+de) — everything else (XML export/import, list rendering, dialog field-hiding, target harvesting) already keys off `isMarkerType()` and picks new types up automatically once that's widened. No test suite exists for this file; verify with a Playwright smoke test (`python -m http.server` + headless chromium) rather than assuming — a static app has no build step to catch typos.

- **Project:** FS25_WorkflowManager
- **HUD show/hide architecture:** `WMHud:update(dt)` polls every frame to auto-hide after 3s when current vehicle has no active workflow. Re-show on vehicle entry is handled by `WorkflowManagerSpec:onRegisterActionEvents()` (fires when player enters and takes control of a vehicle) — NOT by the update loop, because `g_currentMission.controlledVehicle` may not be populated yet when update() first runs after a vehicle switch.
- **FS25 `wm_hBox` alignment:** `wm_hBox` has `elementSpacing=10px` and `alignmentX=center`. Rows with different child counts center at different X positions. Always use 2 children per row (label + content wrapper) with identical declared widths for consistent alignment. For list+slider rows, put both inside a no-spacing inner BoxLayout as one child.
- **FS25 `MultiTextOption` effective width:** A 500px `MultiTextOption` has ~40px consumed by arrow buttons, leaving ~460px visible text area. Match `TextInput` widths to 460px (with a 40px spacer) to align visually with dropdowns.
- **FS25 slider pattern:** `SmoothList` + `ThreePartBitmap (fs25_listSliderBox)` + `Slider` always in a `flowDirection="horizontal"` BoxLayout; list width = container width − 40px (slider).
- **Adding a new AD-driven step type (2026-07-13, Park precedent):** every place that special-cases `WorkflowManager.STEP_AUTODRIVE` inside `WorkflowExecutor.lua` for *tracking* purposes (`onADFinishedEvent` completion match, the completion-poll dispatcher, `pauseCurrentStep`/`resumeCurrentStep`/`stopCurrentStep` dispatch, and `resolvePendingADStart`'s hardcoded `startAutoDriveStep` call) must be widened with an `or ... == STEP_<NEW>` branch, or a new AD-backed step type will silently reuse AD's tracking but break pause/resume/stop or get routed through the wrong start function on a deferred/resumed start. Resume-from-save paths (`activeData.currentStepType = step.type` after reload) need no change since they copy the real step type verbatim — the widened checks handle it. Grep for `STEP_AUTODRIVE` across `WorkflowExecutor.lua` to find every site.
- **`isMarkerStepType` vs new `isTargetlessStepType`:** `isMarkerStepType` means "no AD/CP job" (pure pass-through sync markers) — don't widen it for a step type that still launches a real AD/CP job. Introduced `WorkflowManager:isTargetlessStepType` (`isMarkerStepType(t) or t == STEP_PARK`) for the separate concern of "no user-editable target/action field," used by `WorkflowStorage`, `WMEditorDialog`, `WMHud`, and `WMStepDialog` display/save logic. `WorkflowStorage.lua` keeps its own file-local copy of this predicate (decoupling pattern, see 2026-06-23 entry below) — update both when adding another targetless step type.

## Do-Not-Repeat

[2026-06-24] `isLeaderSyncSatisfied` returns true when `leaderVehicle == nil`, which means "no leader configured". But `pendingLeaderXmlIndex` / `pendingLeaderWorkflowId` set means "leader exists but not yet resolved". Always add the pending check FIRST so the follower blocks at WAIT_FOR_LEADER until the wait poller resolves the reference:
```lua
if activeData.pendingLeaderXmlIndex ~= nil or activeData.pendingLeaderWorkflowId ~= nil then return false end
if activeData.leaderVehicle == nil then return true end
```
Without this, any tight race at map load (follower's onPostLoad runs before leader's) causes the follower to silently pass through its WAIT_FOR_LEADER gate.


[2026-06-17] **SUPERSEDED — dummy hold replaced by raiseActive().** `startDummyHold` and `dummyHelperActive` are GONE. The vehicle-sleep problem is solved by calling `vehicle:raiseActive()` in `WMExecutor:update()` every 500ms for all `activeVehicles`. A global wait poller (`ensureWaitPollerActive` / `globalWaitPoller`) was planned but abandoned — raiseActive() is sufficient. Do NOT introduce `ensureWaitPollerActive` or `stateModule:setActive()` calls for wait states — they are either missing or cause AD to auto-start on reload.

[2026-06-26] `ensureWaitPollerActive()` does not exist in WorkflowExecutor.lua. Any call to it crashes with "attempt to call a nil value". The method was planned (cerebrum mentioned it) but never implemented. raiseActive() in the update loop is sufficient. Do NOT add calls to `WMExecutor:ensureWaitPollerActive()` anywhere. Do NOT add it to test stubs (stubs should match production, not mask the absence).


[2026-05-21] Calling `SmoothList:reloadData()` inside `onSelectionChanged` (or any callback that fires during `mouseEvent` processing) without an `isFiltering` guard causes infinite recursion → `GuiElement.lua:1198: stack overflow`. Always wrap any `reloadData()` call inside a selection callback with `self.isFiltering = true` / `false`.

[2026-05-21] In FS25, `SmoothList.onSelectionChanged` fires during `mouseEvent`. If `reloadData()` is called inside that callback, the engine re-enters `mouseEvent` → `onSelectionChanged` → `reloadData()` → infinite loop. This applies to ALL SmoothList selection callbacks, not just multi-select ones.

[2026-04-10] When deactivating a dummy helper on pause, always call `setActive(false)` AND skip `pauseCurrentStep` entirely (`wasDummy` guard). `pauseCurrentStep` falls back to `currentStepType` from the last real sub-step, which calls `HoldDriving` and blocks player control even after `setActive(false)`.

[2026-04-10] `justStoppedAD` was not cleared in `resetStepTrackingState`. This caused a spurious `pendingADStart` deferral whenever `onMainStepChanged` fired on an idle support vehicle, making the first real sub-step appear to not start. Fix: always clear `justStoppedAD` (and `dummyHelperActive`) in `resetStepTrackingState`.

[2026-04-10] `vehicle.ad.drivePathModule.isPaused` is a **boolean field**, not a method, in the current AD version. Always check `type(...) == "function"` before calling any AD drivePathModule member. Same pattern may apply to other AD module fields.

[2026-04-10] `ADDrivePathModule.PAUSE_TIMEOUT = 3000 ms` — `HoldDriving` only pauses AD for 3 seconds before it auto-resumes. Do NOT use `startRoute + HoldDriving` as a dummy idle helper; the timeout causes the vehicle to start driving. Instead, call `vehicle.ad.stateModule:setActive(true)` directly (via pcall) to keep AD's subsystem alive without a real route. Deactivate with `setActive(false)` when real work starts.

[2026-04-09] HUD re-show on vehicle switch must use `onRegisterActionEvents` in WorkflowManagerSpec, NOT `update()` polling. The `update()` loop's `getActiveWorkflow()` doesn't reliably see the new `controlledVehicle` immediately after a switch. `onRegisterActionEvents` fires exactly when the player enters and takes control of a vehicle.

[2026-04-09] `checkAndHideHUD()` was calling `WMHud:hide()` immediately on workflow stop, overriding the auto-hide timer. The fix: make it a no-op; let `WMHud:update(dt)` manage all show/hide logic reactively.

[2026-04-09] FS25 `setColor()` does not exist on GUI Text elements — use `setTextColor(r, g, b, a)` instead.

[2026-04-07] Support idle poll must check if main step CHANGED, not just if it has sub-steps. The poll for `waitingForMainStep` ran every update cycle and would immediately restart support on the same main step because it didn't track which step triggered the idle. Fix: use `waitingForMainStepIndex` to record which step was active when idle was entered; only resume when `mainActiveData.currentStep ~= waitingForMainStepIndex`.

[2026-05-14] FS25 DDS compression rules: images with alpha → BC3_UNORM (DXT5); fully opaque images → BC1_UNORM (DXT1). Uncompressed RGBA (Pillow default) is rejected as "unknown" compression. BC1/DXT1 on alpha-channel textures corrupts transparency.

[2026-05-14] FS25 `Overlay.new()` and `createImageOverlay()` DO accept DDS for GUI overlays. BC3_UNORM 32×32 icon DDS files work correctly with `Overlay.new`; R8G8B8A8_UNORM DDS works with `createImageOverlay` for the white background texture. Use properly-formed DDS (BC3_UNORM for alpha textures ≥4×4, BC1_UNORM for opaque ≥4×4. Keep all source PNGs at least 4×4 to enable block compression) — eliminates "raw format" and CPU mip-generation warnings. Source PNGs live in `_art/textures/`; generate DDS with `tools/png_to_dds.py`.

[2026-05-26] Never call `self:close()` synchronously inside a dialog's `onOpen()` in FS25. Closing mid-open (before `g_gui` finishes the open transition / input-context push) corrupts the input-context stack → no inputs recognized afterward (HUD/menu can't be closed). If a dialog might have nothing to show, decide BEFORE `g_gui:showDialog`: build the data first and skip showing the dialog when empty (call the callback directly). WMLeaderVehicleSelectDialog now exposes `buildVehicleList()` for this pre-check.

[2026-06-06] In Lua 5.1, `local vehicle = { ... }` does NOT allow closures inside the table literal to capture `vehicle` as an upvalue — it resolves to a global instead. Always declare the local first (`local vehicle`), then assign (`vehicle = { ... }`). This applies to VehicleMock and any other mock that has methods closing over the object being constructed.

[2026-05-21] All WM dialog XML files must use `inputContext="MENU"` (a standard registered FS25 context), NOT custom names like `inputContext="DIALOG_WMEditorDialog"`. Unregistered context names silently fail to activate, leaving the current context as `""`. TextInputElement then pushes TEXT_INPUT with `""` as the saved previous context. On focus-leave (e.g. clicking a SmoothList) it tries to revert to `""` which is undefined → warning + input system corruption → no inputs recognized after dialog closes.

[2026-06-08] `stateModule:setStartHelper(true)` must be called AFTER `AutoDrive:StartDriving` (via `ADIntegration:startRoute`). AD's `StartDriving` resets the `startHelper` flag as part of route initialization. Calling `setStartCPOnCompletion` before `startRoute` means AD silently wipes the flag → CP never auto-starts at target → refill/seed workflows stall. Pattern matches `applyWorkflowSettings`, which already had this "apply after StartDriving" comment.

[2026-06-23] Leader/follower sync is expressed as explicit marker step types — `STEP_WAIT_FOR_LEADER` (follower gate) and `STEP_UNLOCK_FOLLOWER` (leader milestone), paired by ordinal (k-th wait ↔ k-th unlock). They are pass-through steps (no AD/CP job): the wait branch in `executeCurrentStep` calls `WMExecutor:isLeaderSyncSatisfied` then either `onStepCompleted` (proceed) or sets `STATUS_WAITING_FOR_LEADER`; the unlock branch always `onStepCompleted`. `buildSyncMaps` keys off `step.type`, not the old `isSyncTarget/isSyncSource` flags (removed). Sync is opt-in: a workflow with no markers never waits.

[2026-06-23] `WorkflowManager:getStepTypeLabel(type)` / `isMarkerStepType(type)` are the single source for rendering/branching on step type — use them instead of `type == STEP_AUTODRIVE and "AutoDrive" or "Courseplay"` ternaries (which mislabel the two marker types). Touch-points: WorkflowEditorGUI, WMEditorDialog, WMHud, WMConsoleCommands.

[2026-06-23] Unit-test specs stub `_G.WorkflowManager` themselves (NOT the real module): `WorkflowExecutor_spec.lua` (STATUS_*/STEP_* constants + `broadcastState`) and `WorkflowStorage_spec.lua` (minimal stub + STEP_* constants). Adding a new `WorkflowManager.STEP_*` constant or a called method MUST be mirrored in these stubs or tests fail with "unknown step type"/nil-index. WorkflowStorage avoids method coupling via a file-local `isMarkerStepType` that only reads the constants.

[2026-06-23] Storage needs `WorkflowManager#formatVersion` (absent=1, current=2) to migrate. The old save only wrote `isSyncTarget/isSyncSource` when `false`, so an all-default v1 workflow is byte-identical to a new no-marker v2 workflow — version is the only reliable "needs migration" signal. `migrateSyncFlagsToMarkers` inserts a wait marker before each former sync-source step and an unlock marker before each former sync-target step (default true). Migration tests for OTHER concerns (legacy `#fillType`, linked-workflow) must write `formatVersion=2` in their XML to isolate.

[2026-07-13] Never use a positional/index-based identity (array position, XML node index) to reference a *different* entity across separate save files — only the identity's stability *within one load* was verified, not across sessions where the referenced collection's composition can change. For cross-session vehicle references, use `vehicle.uniqueId` (FS25's own engine-assigned, save-stable id — visible as `uniqueId="..."` on `<vehicle>` in vehicles.xml) instead. See bug-119 in buglog.json.

[2026-07-04] Leader-gone detection (`isLeaderSyncSatisfied`'s "leader finished/stopped/restarted → free follower" branch) previously only ran when the follower was blocked at a `wait_for_leader` step. Extracted that branch into `WMExecutor:refreshLeaderLink(activeData)` and now call it unconditionally every poll tick (in `WMExecutor:update()`, alongside `tryResolvePendingLeader`) so a follower running its own step (not at a wait marker) also detaches `leaderVehicle`/`linkedLeaderExecution` promptly when the leader finishes, instead of only on its next wait-marker hit.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->

[2026-04-09] Support step visibility: when a support sub-step starts automatically (triggered by main advancing), the player in another vehicle has no HUD feedback. This is known and intentional — no cross-vehicle notification was added (user explicitly declined).

[2026-07-13] New "Park" step type (`WorkflowManager.STEP_PARK = "park"`): drives the vehicle to its AutoDrive-configured park position instead of a manually-picked destination. Resolution order confirmed by the user: rear-attached implement's `advd.parkDestination` first (`vehicle:getAttachedImplements()[1].object` — no recursive chain-walking), falling back to the vehicle's own `advd.parkDestination`. If neither is configured, the step **fails** (`handleStepError`) rather than skipping silently — user explicitly chose fail-over-skip. AD's own park sentinel is `unloadDestinationID = -3` on `AutoDrive:StartDriving`, and the target marker id must be pushed into `vehicle.ad.stateModule:setParkDestinationAtJobFinished(id)` *before* calling `StartDriving` (AD reads that field internally for the `-3` branch, not the `destinationID` param). Implemented as `ADIntegration:startParkRoute`/`getRearAttachedObject`/`getObjectParkDestination`/`getVehicleParkDestinationId` in `AutoDriveIntegration.lua`, `WMExecutor:startParkStep` in `WorkflowExecutor.lua`.

[2026-07-13] New "Refuel" and "Repair" step types (`STEP_REFUEL`, `STEP_REPAIR`). Both targetless like Park, but unlike Park neither has a per-vehicle *stored* destination in AD — both are resolved dynamically at start time: `ADTriggerManager.getClosestRefuelDestination(vehicle, true)` (dot-call, no self) and `AutoDrive:getClosestRepairTrigger(vehicle)` (colon-call). Refuel's `unloadDestinationID = -2` sentinel on `AutoDrive:StartDriving` is a near no-op (just calls `getCurrentMode():start()`) — the caller must pre-arm `vehicle.ad.stateModule:setMode(AutoDrive.MODE_DRIVETO)` and `vehicle.ad.onRouteToRefuel = true` *before* calling `StartDriving`, and AD's own `ADTaskModule:RefuelIfNeeded()` (runs every tick when the vehicle has no active task) enqueues the actual `RefuelTask`. Repair has **no `StartDriving` sentinel at all** — bootstrapped by calling `vehicle:startAutoDrive()` directly (the same call `DriveToMode:start()` makes internally when AD isn't yet active) after setting `onRouteToRepair = true`; verified safe against `AutoDrive:startAutoDrive()`'s own side effects (`Specialization.lua:1104`), which only resets `onRouteToPark = false`, never `onRouteToRefuel`/`onRouteToRepair`. Both `RefuelTask:finished()` and `RepairTask:finished()` call `vehicle:stopAutoDrive()` on completion (same as Park's task), so the existing `ADIntegration:isRouteComplete` (`not isActive()`) polling fallback detects completion with zero new logic. **User-chosen fallback semantics differ from Park**: when AD's refuel-station lookup returns nil, it's ambiguous between "no matching station" and "already ≥90% full" (AD itself conflates these) — user chose to treat this as **instant step success** (`onStepCompleted`), not `handleStepError`, unlike Park/Repair where an unresolvable destination is a real failure. `ADIntegration:startRefuelRoute` therefore returns two values (`success, skipped`) instead of one boolean. Extracted `WorkflowManager:isAutoDriveTrackedStepType(stepType)` (AUTODRIVE/PARK/REFUEL/REPAIR) to replace the growing `STEP_AUTODRIVE or STEP_PARK` OR-chains at every `WorkflowExecutor.lua` tracking site (`onADFinishedEvent`, completion poll, `pauseCurrentStep`/`resumeCurrentStep`/`stopCurrentStep`, `resolvePendingADStart`'s type-aware dispatch) — any *future* AD-driven targetless step type should be added to this one helper, not scattered.
