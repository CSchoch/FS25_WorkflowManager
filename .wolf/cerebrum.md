- **Vehicle sleep handling (updated 2026-08-15):** `raiseActive()` called every 500ms in `WMExecutor:update()` (inside the throttle, NOT per-frame — per-frame was pure waste) for active vehicles is sufficient to keep waiting vehicles awake. PAUSED vehicles are deliberately allowed to sleep, except while `autoResumeUntil` is set (post-load window where AD/CP may still auto-start). A separate global wait poller (`g_currentMission:addUpdateable`) is NOT needed and NOT implemented. - **Leader vehicle save/restore identity (SUPERSEDED 2026-07-13):** The XML index parsed from `savegame.key` (`wmXmlIndex`, stored as `#leaderVehicleXmlIndex`) is only stable *within one load* — it is NOT stable across separate save sessions. If the composition/order of `vehicles.xml` changes between saves (vehicle bought/sold, implement added elsewhere in the list, etc.), the same numeric index can point to a completely different vehicle on the next load. This caused bug-119 ("Steyer tractor lost its leader"): a stale index resolved to an unrelated vehicle with no workflow, so the pending-leader poller could never match it and the follower was stuck in `waiting_for_leader` forever. **Fix:** use the vehicle's own engine-assigned `vehicle.uniqueId` (same value as the `uniqueId="..."` attribute FS25 already writes on every `<vehicle>` element) as the primary leader identity — read/compare it directly off the live vehicle object, do NOT mirror/cache it under a new field name. Saved as `#leaderVehicleUniqueId`, with `pendingLeaderUniqueId` mirroring the existing `pendingLeaderXmlIndex`/`pendingLeaderWorkflowId` deferred-resolution fields. The old `#leaderVehicleXmlIndex` → legacy `#leaderVehicleIndex` → legacy `#leaderWorkflowId` chain is kept as a read-only fallback for saves written before this fix, unchanged. Do NOT use `g_currentMission.vehicles` array position either (unstable — map scripts can prepend vehicles, shifting indices). Do NOT use workflow ID alone (ambiguous — multiple vehicles can run the same workflow).

### FS25 dialogs: never open two mod dialogs at once (2026-08-30)
FS25 pushes one input context per open dialog (`DIALOG_<guiName>`), and `TextInputElement`
pushes a temporary `TEXT_INPUT` on focus. In a dialog opened on top of another dialog, a
focused TextInput records an **empty** previous context, so its focus-leave `revertContext`
fails and TEXT_INPUT is never popped. From there every push/pop is off by one and the game
ends up parked in a dead `DIALOG_*` context after everything closes: no keyboard, and no
mouse either once `WMHud:onDialogClosed` releases the cursor. Rule: close the parent dialog
BEFORE showing a child, and re-show the parent from the child's callback (the child closes
itself first, so they never overlap) - `WMEditorDialog:suspendForChildDialog` /
`resumeAfterChildDialog`, `WorkflowManager:reopenEditorDialog`. AutoDrive and Courseplay
follow the same one-dialog-at-a-time discipline.

Refuel's `unloadDestinationID = -2` sentinel on `AutoDrive:StartDriving` is a near no-op (just calls `getCurrentMode():start()`) — the caller must pre-arm `vehicle.ad.stateModule:setMode(AutoDrive.MODE_DRIVETO)` and `vehicle.ad.onRouteToRefuel = true` *before* calling `StartDriving`, and AD's own `ADTaskModule:RefuelIfNeeded()` (runs every tick when the vehicle has no active task) enqueues the actual `RefuelTask`. Repair has **no `StartDriving` sentinel at all** — bootstrapped by calling `vehicle:startAutoDrive()` directly (the same call `DriveToMode:start()` makes internally when AD isn't yet active) after setting `onRouteToRepair = true`; verified safe against `AutoDrive:startAutoDrive()`'s own side effects (`Specialization.lua:1104`), which only resets `onRouteToPark = false`, never `onRouteToRefuel`/`onRouteToRepair`. Both `RefuelTask:finished()` and `RepairTask:finished()` call `vehicle:stopAutoDrive()` on completion (same as Park's task), so the existing `ADIntegration:isRouteComplete` (`not isActive()`) polling fallback detects completion with zero new logic. **User-chosen fallback semantics differ from Park**: when AD's refuel-station lookup returns nil, it's ambiguous between "no matching station" and "already ≥90% full" (AD itself conflates these) — user chose to treat this as **instant step success** (`onStepCompleted`), not `handleStepError`, unlike Park/Repair where an unresolvable destination is a real failure. `ADIntegration:startRefuelRoute` therefore returns two values (`success, skipped`) instead of one boolean. Extracted `WorkflowManager:isAutoDriveTrackedStepType(stepType)` (AUTODRIVE/PARK/REFUEL/REPAIR) to replace the growing `STEP_AUTODRIVE or STEP_PARK` OR-chains at every `WorkflowExecutor.lua` tracking site (`onADFinishedEvent`, completion poll, `pauseCurrentStep`/`resumeCurrentStep`/`stopCurrentStep`, `resolvePendingADStart`'s type-aware dispatch) — any *future* AD-driven targetless step type should be added to this one helper, not scattered.
