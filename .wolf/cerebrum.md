- **Resources the mod forces on the game must be released by the mod, at a defined moment — and that moment is a deliberate user-facing decision, not an implementation detail.** WM forces the mouse cursor on when Start auto-closes the main dialog (HUD becomes the click surface). The user specified the release point: **when the last WM dialog in the chain closes**, explicitly NOT when the HUD auto-hides ("Do not hide the cursor on Auto Hide Hud") — the HUD auto-hides 3s after a workflow ends and yanking the cursor away there is wrong. Implemented in `WMHud`: `setMouseCursorActive(active)` + `mouseCursorForced` flag (never switch off a cursor AutoDrive/Courseplay turned on), and `onDialogOpened`/`onDialogClosed` counting `openDialogCount`; every WM dialog calls them from `onOpen`/`onClose`. The HUD itself is **never** part of that count: closing it manually (X button / toggle key) goes through `closeManually()` and always drops the cursor, while the auto-hide path calls plain `hide()` and leaves it. Prefer this ownership pattern over fire-and-forget global state changes. **Addendum 2026-08-15:** a grant requested while `openDialogCount > 0` (start flow stacking a leader/mode-select dialog) is deferred via `pendingCursorGrant` and materialized by `onDialogClosed` when the chain fully closes — granting immediately gets revoked by the chain's own close-at-zero release. `closeManually()` cancels a pending grant.

- **Courseplay FileSystem shape (`FS25_Courseplay/scripts/courseManager/FileSystem.lua`):** `FileSystem.rootDirectoryView` is a `DirectoryView` at **level 0**, and `fixCourseStorageRoot()` puts a `Singleplayer` folder at level 1 underneath it — so a course in field folder `F34` is level 3 and its root-relative path is `Singleplayer/F34/Kalken`, not `F34/Kalken`. `DirectoryView:getEntries()` returns only direct children (dirs sorted first, then files), each a `FileSystemEntityView` with `.name`, `.level`, `.parent`, `.entity` and an `isDirectory()` **method**. - **Stored course paths must be matched as path SUFFIXES.** Workflow steps hold whatever path was current when they were authored; the root prefix has changed across versions. Matching only the base name across the whole tree is unsafe — field folders routinely contain identically named courses (`F09/Kalken`, `F34/Kalken`), so a bare-name match loads the wrong field's course silently. See `CPIntegration:findCourseEntry`.
- **Vehicle sleep handling (updated 2026-08-15):** `raiseActive()` called every 500ms in `WMExecutor:update()` (inside the throttle, NOT per-frame — per-frame was pure waste) for active vehicles is sufficient to keep waiting vehicles awake. PAUSED vehicles are deliberately allowed to sleep, except while `autoResumeUntil` is set (post-load window where AD/CP may still auto-start). A separate global wait poller (`g_currentMission:addUpdateable`) is NOT needed and NOT implemented. Do not introduce `ensureWaitPollerActive` / `globalWaitPoller` — they were planned but abandoned; raiseActive() in the update loop handles all WAITING states.
- **Leader vehicle save/restore identity (SUPERSEDED 2026-07-13):** The XML index parsed from `savegame.key` (`wmXmlIndex`, stored as `#leaderVehicleXmlIndex`) is only stable *within one load* — it is NOT stable across separate save sessions. If the composition/order of `vehicles.xml` changes between saves (vehicle bought/sold, implement added elsewhere in the list, etc.), the same numeric index can point to a completely different vehicle on the next load. This caused bug-119 ("Steyer tractor lost its leader"): a stale index resolved to an unrelated vehicle with no workflow, so the pending-leader poller could never match it and the follower was stuck in `waiting_for_leader` forever. **Fix:** use the vehicle's own engine-assigned `vehicle.uniqueId` (same value as the `uniqueId="..."` attribute FS25 already writes on every `<vehicle>` element) as the primary leader identity — read/compare it directly off the live vehicle object, do NOT mirror/cache it under a new field name. Saved as `#leaderVehicleUniqueId`, with `pendingLeaderUniqueId` mirroring the existing `pendingLeaderXmlIndex`/`pendingLeaderWorkflowId` deferred-resolution fields. The old `#leaderVehicleXmlIndex` → legacy `#leaderVehicleIndex` → legacy `#leaderWorkflowId` chain is kept as a read-only fallback for saves written before this fix, unchanged. Do NOT use `g_currentMission.vehicles` array position either (unstable — map scripts can prepend vehicles, shifting indices). Do NOT use workflow ID alone (ambiguous — multiple vehicles can run the same workflow).
- **`onPostLoad` ordering:** FS25 calls `onPostLoad` for each vehicle as it loads — order is not guaranteed. A vehicle that has a leader may load BEFORE the leader, so leader resolution must be deferred. `tryResolvePendingLeader` runs every 500ms in the WMExecutor update loop; the standard update tick handles all pending resolution without a separate poller.

### FS25 dialogs: never open two mod dialogs at once (2026-08-30)
FS25 pushes one input context per open dialog (`DIALOG_<guiName>`), and `TextInputElement`
pushes a temporary `TEXT_INPUT` on focus. In a dialog opened on top of another dialog, a
focused TextInput records an **empty** previous context, so its focus-leave `revertContext`
fails and TEXT_INPUT is never popped. From there every push/pop is off by one and the game
ends up parked in a dead `DIALOG_*` context after everything closes: no keyboard, and no
mouse either once `WMHud:onDialogClosed` releases the cursor. Rule: close the parent dialog
BEFORE showing a child, and re-show the parent from the child's callback (the child closes
itself first, so they never overlap) - `WMEditorDialog:suspendForChildDialog` /
`resumeAfterChildDialog`, `WorkflowManager:reopenEditorDialog`. AutoDrive and Courseplay
follow the same one-dialog-at-a-time discipline.

[2026-07-14] **Every bare AD global reference in `AutoDriveIntegration.lua` must have an `FS25_AutoDrive.<Name>` fallback, or it will be nil in the real game despite existing in AD's source.** FS25 sandboxes each mod's top-level globals into an `FS25_<ModName>` table; from WM's own environment, an AD global like `ADTriggerManager` (a real global inside `FS25_AutoDrive/scripts/Manager/TriggerManager.lua`, `ADTriggerManager = {}`) is NOT visible as a bare global — only `AutoDrive` itself gets bridged in via `ADIntegration:checkAvailability()`'s explicit `AutoDrive = FS25_AutoDrive.AutoDrive` assignment. `getDestinations()` already had the right pattern (`ADGraphManager or FS25_AutoDrive.ADGraphManager`), but `startRefuelRoute` (added in the bug-137 Refuel/Repair work) checked bare `ADTriggerManager` only, so it silently failed in-game (`ADTriggerManager not available`, bug-148) even though unit tests passed — the spec mocks `_G.ADTriggerManager` directly and never exercises the namespace-resolution path. Fixed with `local triggerManager = ADTriggerManager or (FS25_AutoDrive and FS25_AutoDrive.ADTriggerManager)`. **When adding any new AD sub-manager reference, use this same dual-check pattern, never a bare-global-only check** — and note the test mock gap means tests alone can't catch a missing fallback.

[2026-07-13] New "Refuel" and "Repair" step types (`STEP_REFUEL`, `STEP_REPAIR`). Both targetless like Park, but unlike Park neither has a per-vehicle *stored* destination in AD — both are resolved dynamically at start time: `ADTriggerManager.getClosestRefuelDestination(vehicle, true)` (dot-call, no self) and `AutoDrive:getClosestRepairTrigger(vehicle)` (colon-call). Refuel's `unloadDestinationID = -2` sentinel on `AutoDrive:StartDriving` is a near no-op (just calls `getCurrentMode():start()`) — the caller must pre-arm `vehicle.ad.stateModule:setMode(AutoDrive.MODE_DRIVETO)` and `vehicle.ad.onRouteToRefuel = true` *before* calling `StartDriving`, and AD's own `ADTaskModule:RefuelIfNeeded()` (runs every tick when the vehicle has no active task) enqueues the actual `RefuelTask`. Repair has **no `StartDriving` sentinel at all** — bootstrapped by calling `vehicle:startAutoDrive()` directly (the same call `DriveToMode:start()` makes internally when AD isn't yet active) after setting `onRouteToRepair = true`; verified safe against `AutoDrive:startAutoDrive()`'s own side effects (`Specialization.lua:1104`), which only resets `onRouteToPark = false`, never `onRouteToRefuel`/`onRouteToRepair`. Both `RefuelTask:finished()` and `RepairTask:finished()` call `vehicle:stopAutoDrive()` on completion (same as Park's task), so the existing `ADIntegration:isRouteComplete` (`not isActive()`) polling fallback detects completion with zero new logic. **User-chosen fallback semantics differ from Park**: when AD's refuel-station lookup returns nil, it's ambiguous between "no matching station" and "already ≥90% full" (AD itself conflates these) — user chose to treat this as **instant step success** (`onStepCompleted`), not `handleStepError`, unlike Park/Repair where an unresolvable destination is a real failure. `ADIntegration:startRefuelRoute` therefore returns two values (`success, skipped`) instead of one boolean. Extracted `WorkflowManager:isAutoDriveTrackedStepType(stepType)` (AUTODRIVE/PARK/REFUEL/REPAIR) to replace the growing `STEP_AUTODRIVE or STEP_PARK` OR-chains at every `WorkflowExecutor.lua` tracking site (`onADFinishedEvent`, completion poll, `pauseCurrentStep`/`resumeCurrentStep`/`stopCurrentStep`, `resolvePendingADStart`'s type-aware dispatch) — any *future* AD-driven targetless step type should be added to this one helper, not scattered.
